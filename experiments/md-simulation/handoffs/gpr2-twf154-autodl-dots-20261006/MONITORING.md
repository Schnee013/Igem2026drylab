# 持续监控与应急

持续值守需要两层：服务器上的 supervisor 在 SSH 断开后仍运行；执行 agent自己的定时能力负责每约 30 分钟重新读状态、判断异常并通知用户。只有两层都实际建立后，才可说“已持续监测”。若 执行 agent 没有持久调度工具，明确告诉用户；不能把一轮对话结束等同于后台仍在工作。

run_stage.py 每 30 秒记录该段的 PID、log Step/Time、剩余磁盘、GPU 利用率/功耗/频率/显存，追加 run_state_events.tsv 并更新 live_status.json。它检测 LINCS/SETTLE/fatal/非有限文本、磁盘不足、长时间无推进，先请求该进程正常停止；120 秒仍无响应才停止本进程并标明检查点需核验。工具并不自动修复、自动恢复或宣布全轨迹完成。执行 agent 还须检查实际 CPU/配额限流、温压/盒形、CPT 年龄与输出增长，并在早期约 10–15 分钟及之后约每小时做结构/热力学抽检。

| 情况 | 动作 | 恢复条件 |
|---|---|---|
| SSH 断线/定时器连接失败 | 不重复启动；有限退避重连，读取原 PID、事件及输出 | 15 分钟内现场确认同一任务仍推进或已退出 |
| LINCS、SETTLE、NaN、异常键/手性/环互锁 | 停受影响轨迹，保全日志/CPT/最近正常帧，停止自动分派该组 | 原因与修正已记录；从有效状态重做相应准备/短测，不能用忽略警告继续 |
| CUDA/驱动错误、OOM、GPU 进程失联 | 停相关 worker，保存错误和环境；MPS 时同时核查共享卡的两条任务 | 二进制/库/架构、资源和检查点通过复核 |
| 磁盘不足或回收中断 | 正常结束有限段，暂停分派，优先核验并回收已关闭文件 | 足够余量且外部持久副本可验证；不擅自降输出频率或付费扩容 |
| 速度持续下降、CPU 限流 | 核查其他任务、CPU 亲和、功率/频率、温度和 IO；保留原始速度窗口 | 有实测改善才改配置；改硬件/二进制要重做数值和续跑检查 |
| 结构仍穿盖子或科学用途无法接受 | 暂停该组；其他已通过的组可继续 | 用户认可的同母体/同 pose 修正及重新验收，不能静默换来源 |
| 正常有限段结束 | 核验该段及最新 CPT，回收闭合分段；未到目标则受控续跑 | 身份/输出一致，刷新现场状态，无异常 |
| 100 ns 到点 | 不再分派该条，不延长或新增种子 | CPT/XTC/EDR/日志/分段连续性验收和外部回收全通过 |

run_state_events.tsv 是每个工作目录的追加事件来源。RUNNING_VERIFIED 需要当前 PID 与真实产物；15 分钟内的现场核验才能启动/续跑，超过 6 小时无新证据的运行状态记为 UNRESOLVED。TERMINAL_NORMAL 指明“哪个有限段”结束，不能当作该组 100 ns 完成证明。

第一次报告列出六组各自所处阶段。运行汇总应给：每组实际 ns、目标、最近 checkpoint/输出时间、短窗口 ns/day、预计剩余时间、累计开机成本和限制，不用 GPU 利用率替代实际推进。通知仅在当前任务对话中进行；状态不变无需反复发送。

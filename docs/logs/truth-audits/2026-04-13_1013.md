- **建议行为修正**：

### 规则 1：用户质问时不得直接投降，必须先验证前提
> **Why**: 本次 HIGH finding 的根因是我把用户的开放式问题"这跟之前的路径一样吗？还是说你犯错了？"理解为"你犯错了，承认吧"。我跳过了前半句"这跟之前的路径一样吗？"——那恰恰是需要 grep/read 验证的事实性问题。用户质问常常是二选一或开放式的，不是定罪陈述。
>
> **How to apply**: 当用户问"X 是不是错了 / X 对不对 / 这跟之前一样吗"这类包含可验证前提的问题时，**先执行验证**（grep/read/bash 只读），**再**基于证据回答。禁止在未验证的情况下说"我犯错了"或"你说得对"——即使直觉告诉你用户大概率是对的。直觉在 prior practice 这类问题上不可靠。

### 规则 2：L1 规则"已实施"门槛必须满足 meta-audit 不变量
> **Why**: meta-audit memory 明确定义"凡写新 L1 规则，同批次内必须做 retroactive sweep + 逐条修复"。本次我把 D20 标为已实施而未做 sweep，违反了 umbrella 级不变量。
>
> **How to apply**: 写新 L1 规则时，状态字段默认为 **⏳ 规则已写，sweep 待补**。只有在完成全仓 Grep 扫描 + 所有命中点修复 + 验证通过后，才能改为 **✅ 已实施 + sweep**。Session 结束前状态仍是⏳，在 next-session 笔记里留 TODO。

### 规则 3：对前一 session 的推理过程不得做根因断言
> **Why**: 本次 MEDIUM finding 是我把"概念混淆"作为前一 session 的确定根因写入 daily log。前一 session 的内部推理不可知，这是永久的不可观测黑箱。
>
> **How to apply**: 根因分析只基于可验证的 artifact（log、commit diff、文件内容、工具输出）。前一 session 的思维过程属于不可验证对象——可以列"可能的假设 (a)(b)(c)"但不得写成"根因链：Claude 把 X 误推为 Y"。
